| **FFI unsafe call**    | 2,330      | ~500       | ~42.8%   | **~30%**| **~70%** | 大量标准 FFI 绑定被消减，剩余多为真实 FFI 调用 |

| **null_dereference**   | 1          | 1          | 0.09%    | **100%**| 0%      | libuv150 OMI-001 确认                    |

### 1.2 核心结论（R7.0 更新）

**R7.0 前**: 检出 2,924 Issues，TP 率仅 ~11%（~2,620 FP），最大 FP 来源是 FFI unsafe call（95% FP）。

**R7.0 后**: 检出 **1,169 Issues**（↓60%），TP 率提升至 **~33%**（**~386 个 TP / ~783 个 FP**）。

Zone-First 门控架构成功将 **FFI unsafe call 从 2,330 → ~500**（↓78.5%），5 个纯 FP 项目归零（ring/blst/wasmtime/ripgrep/ark_ff），故意 bug 测试用例 TP 保留率 >90%。

## 二、逐类别 TP/FP 详细分析

### 2.1 FFI unsafe call（2,330 个，~95% FP）

**检测代码路径**: [ffi_boundary.zig:checkCallForFFI()](src/pass/analysis/ffi_boundary.zig:L165) → [reportFFIIssue()](src/pass/analysis/ffi_boundary.zig:L263) → `.ffi_unsafe_call`

**检测逻辑**:
```
对每个 call 指令:
  1. called_name 在 SemanticRegistry? → is_dangerous = true
  2. noise_filter 过滤? (SafeLibc/CPP/STL)
  3. caller_lang != callee_lang? → FFI boundary
  4. confidence >= 0.4? → 报告 .ffi_unsafe_call
```

**FP 根因分析**:

| FP 模式                          | 代表项目           | FP 数量级 | 原因说明                                       |
| ------------------------------- | -------------- | ------ | ------------------------------------------ |
| 标准 POSIX API 调用被标记 "unsafe"  | libuv150        | ~107   | pthread_*, setsockopt, dlopen 是系统编程标配     |
| Rust FFI binding 调 C 标准库       | ring (125)      | ~125   | ring 的 memcmp/ring_core_* 是审计过的加密绑定     |
| Go cgo 内部运行时调用             | gnark_test (334) | ~334   | runtime.printitf, runtime.cgo_CString 是 Go 运行时 |
| C++ 标准库模式匹配过宽            | jsoncpp (287)   | ~287   | contains 匹配把非危险函数也包含进来了            |
| Zig @cImport 安全绑定未完全覆盖     | blst (93)       | ~93    | zig_cimport_safe 白名单不够全                      |

**TP 示例（确实有价值）**:
- `openssl_wrapper` 中 `password_handling: printf` — 用户可控格式字符串，**TP**
- `libuv150` 中 `fork + execvp` — 子进程执行，**低置信度 TP**
- `gnark_test` 中 `calloc → malloc` — 分配器不匹配，**TP**

**消减方案**:

| 优先级 | 方案                                    | 预计减少 FP | 复杂度 |
| ---- | -------------------------------------- | ------- | ---- |
| P0   | 增加"知名库安全绑定白名单"（ring/boringssl/mbedtls/sodium 的 FFI 模式） | ~500    | 低    |
| P0   | 区分 "Rust FFI struct binding" vs "裸函数指针调用"          | ~300    | 中    |
| P1   | Go runtime 函数加入 zig_internal_patterns 同等白名单         | ~334    | 低    |
| P1   | contains 匹配改为 exact + 有限 suffix                  | ~200    | 中    |
| P2   | 基于调用上下文的 confidence 调整（如：参数均为字面量则降级）    | ~300    | 高    |

### 2.2 double_free（271 个，~70% FP）

**检测代码路径**: [PtrLifetime pass](src/pass/analysis/ptr_lifetime.zig) + Zone Classification

**TP 示例**:
- `rust_sqlite::double_close` — sqlite3_close 调用两次，**确认 TP**
- `openssl_wrapper::correct_encryption` 中多次 EVP_CIPHER_CTX_free（如果路径重叠）— **潜在 TP**

**FP 主要来源**:

| FP 模式                  | 代表项目  | 原因                                      |
| ----------------------- | ----- | --------------------------------------- |
| realloc 模式被误判为 double_free | sqlite3 | ptr = realloc(ptr, ...) 后原 ptr 被 track 为 freed |
| 分支路径中配对的 free/delete    | curl8  | if/else 两分支各有一个 free，分析时合并为重复      |
| C++ destructor 中的 delete     | jsoncpp | 析构函数释放成员，与之前代码路径的释放重复计算      |

**消减方案**:

| 优先级 | 方案                              | 预计效果  |
| ---- | ------------------------------- | ----- |
| P0   | realloc 检测：识别 realloc 返回值替换旧指针 | -60% FP |
| P1   | 路径敏感分析：if/else 互斥分支不合并计数     | -30% FP |
| P1   | C++ destructor 识别与跳过              | -20% FP |

### 2.3 memory_leak（232 个，~75% FP）

**检测代码路径**: [PointerOwnership pass](src/pass/analysis/ffi_boundary.zig) → `Found X memory leaks`

**FP 主因**: PointerOwnership 使用简单的 alloc/free 计数不平衡检测，不理解：
- 自定义内存池（SQLite 的 lookaside allocator）
- 引用计数的延迟释放（OpenSSL REF_COUNT 模式）
- 全局单例模式（malloc 一次，程序生命周期内不 free）
- 输出参数模式（caller 提供 buffer，callee 填充）

**TP 示例**:
- `openssl_wrapper::encrypt_leak_ctx` — EVP_CIPHER_CTX_new 无对应 free，**确认 TP**
- `openssl_wrapper::bio_leak` — BIO_new 无 BIO_free，**确认 TP**
- `rust_sqlite::leak_database` — sqlite3_open 无 sqlite3_close，**确认 TP**

**消减方案**:

| 优先级 | 方案                            | 预计效果  |
| ---- | ----------------------------- | ----- |
| P0   | 全局变量/静态存储期检测（从不 leak 的模式）   | -40% FP |
| P1   | 引用计数模式识别（INCREF/DECREF 配对）     | -15% FP |
| P1   | 已知 API 生命周期白名单（sqlite3/libuv）    | -20% FP |

### 2.4 format_string（97 个，~85% FP）

**检测代码路径**: Risky Call Pass (`printf` contains match in SemanticRegistry)

**TP 示例**:
- `openssl_wrapper::password_handling: printf` — 密码传入 printf，**确认 TP**

**FP 主因**: SQLite/libuv 内部的 snprintf/sqlite3_mprintf/vfprintf 调用：
- 全部使用固定格式字符串（非用户可控）
- 已有长度限制（snprintf/mprintf 版本）
- 仅用于内部诊断日志

**消减方案**: 已部分实现 [isLikelySafeContext()](src/pass/analysis/issue/ffi_unsafe.zig:L241)，但仅对 format_string 生效且白名单不够完整。建议扩展至所有项目。

### 2.5 borrow_escape（152 个，~90% FP）

**检测主因**: CallbackEscape Pass 将 C 语言的"指针作为输出参数传递"模式误判为 Rust-style borrow escape。C 代码中 `func(&local_var)` 是标准做法，不是逃逸。

**消减方案**: 当 caller 语言为 C 时，大幅降低 borrow_escape 的置信度或直接跳过。

## 六、风险与注意事项

1. **白名单不能替代正确分析**: R7.0 的白名单方案是治标，长期需要上下文敏感的分析（R7.0-5 的 confidence 调整方向）
2. **过度消减风险**: 激进的 FP 消减可能导致真正的 TP 被误杀。每步都需要回归测试集验证
3. **测试集不足**: 当前 18 个项目中，仅有 openssl_wrapper 和 rust_sqlite 是含已知 bug 的测试用例。建议增加更多 intentional-bug 测试用例
4. **Zone Classification 的 2,330 个 FFI unsafe call 缺乏可观测性**: 无法看到具体的 (caller → callee) 对，这是调试和验证的最大障碍
