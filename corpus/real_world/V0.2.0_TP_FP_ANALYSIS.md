### 2.2 变化原因分析

#### 🔥 sqlite3: 730 → 240 (-67%)

**这是最大的单一改进。** Root Cause是 **P0-1 FFIBoundaryPass gate Fix**：

```
Fix前: FFIBoundaryPass.deps = {}  → isRelevantFunction() 始终返回 false
       → 所有 FFI 调用被标记为 "irrelevant"
       → 但 ptr_lifetime 仍然报告这些调用（无门控过滤）
       → 产生大量误报（FFI unsafe call 从 194 个虚假标记变为正确分析）

Fix后: FFIBoundaryPass.deps = {"danger-surface"}
       → DangerSurfacePass 先运行，填充 relevant_functions
       → FFIBoundaryPass 正确识别 FFI Boundary
       → ptr_lifetime 只关注真正危险的Cross-Language调用
       → FFI unsafe call 从 194 → ~60（估算）
```

**类别分解变化**（sqlite3）:

| 类别 | 旧数量 | 新数量(估) | 变化 | 原因 |
|------|--------|-----------|------|------|
| format_string | 80 | ~10 | -88% | mprintf/snprintf 白名单生效 |
| FFI unsafe call | 194 | ~5 | -97% | FFIBoundaryPass 门控修正 |
| borrow_escape | 76 | ~100 | +31% | 检测精度提升后更多被正确分类 |
| memory_leak | 150 | ~53 | -65% | lookaside pool 模式改善 |
| double_free | 156 | ~42 | -73% | realloc/FuzzyMatcher Fix |
| invalid_free | 28 | ~18 | -36% | isCFree 死代码Fix |
| 其他 | 46 | ~12 | -74% | 综合效果 |

#### curl8: 320 → 165 (-48%)

类似 sqlite3，主要受益于 FFIBoundaryPass Fix和 POSIX API 白名单隐含改善。
**FP 重灾区**: inet_pton (13次), __strcpy_chk (3次编译器builtin), setsockopt (7次) — 全部应为 FP。

#### libuv150: 174 → 94 (-46%)

libuv 作为系统库，FFI unsafe call 的减少最为显著（67 → ~25）。
**最大 FP 来源**: __snprintf_chk 在 uv_strerror_r 中出现 **38 次**（一个函数产生 38 个 format_string 报告）— 编译器 builtin，100% FP。

#### openssl_wrapper: 21 → 4 (-81%)

**TP 锚点项目**: 4/4 = **100% TP**，源码注释铁证如山。见 Section 7.1 详细验证。

## 四、其他 Bug Fix效果

### 4.1 P0-2: getOutgoingEdges 悬垂指针

**影响**: call_graph 内部 API，不影响外部可见结果。

**Fix内容**:
```zig
// Before (Bug): 运行时数组拼接 → 悬垂指针
pub fn getOutgoingEdges(...) []CallEdge {
    var result: []CallEdge = &.{};
    result = result ++ &.{edge.*};  // ← 返回栈上临时地址!
}

// After (Fixed): 三种 API 风格
pub fn getOutgoingEdges(...) !ArrayList(CallEdge) { ... }           // 主 API
pub fn forEachOutgoingEdge(...) bool { ... }                   // 零分配迭代
pub fn getOutgoingEdgesSlice(...) ![]CallEdge { ... }          // 切片便利包装
```

**验证**: `zig build test` 通过，无Memory Safety告警。

### 4.2 P1-2: isCppMangledName off-by-one → Rust hash suffix

**影响**: noise_filter.zig 的 Rust/C++ 分类准确性。

**Fix前后对比**:

| Mangled Name | 语言 | 旧判定 (`name[1]=='N'`) | 新判定 (`{N}h{hex}E`) |
|------------|------|------------------------|---------------------|
| `_Z3foo` | C++ | C++ ✅ | C++ ✅ |
| `_ZN3foo3barE` | C++ | **Rust ❌ 误报** | C++ ✅ |
| `_ZN4main17hE` | Rust | Rust ✅ | Rust ✅ |
| `_ZN4myapp17h123abcE` | Rust | Rust ✅ | Rust ✅ |

**效果**: C++ 嵌套命名空间名不再被错误排除。

### 4.3 P1-11: isCFree 死代码

**影响**: semantic_registry.zig 的 free 函数配对准确性。

**Fix**:
```zig
// Before (Bug): "free" 在 patterns 循环中先匹配 → return true
// → 复合词排除逻辑永远不会执行
const free_patterns = [_][]const u8{
    "free", "dealloc", "destroy", ...  // ← "free" 在这里!
};

// After (Fixed): "free" 单独处理，带边界检查
const free_patterns = [_][]const u8{
    "dealloc", "destroy", "release", ...  // ← 无 "free"
};
// 单独检查 "free"，带复合词排除
const idx = std.mem.indexOf(u8, name, "free") orelse return false;
if (idx > 0 and isAlphaNum(name[idx - 1])) return false;
```

### 4.4 P2-6: extractLibPrefix 冗余条件

**影响**: memory_graph_fuzzy.zig 的 alloc/free 配对匹配。

**Fix**: `fn_name[end] != '_'` 从 3 次重复去重为 1 次。

**效果**: 代码清晰度提升，功能不变。

| OmniScope 假设 | Go/TinyGo Actual | 冲突? |
|---------------|---------------|-------|
| malloc 必须配对 free | GC 自动回收内存 | **✅ 冲突** |

| null pointer 需要显式检查 | Go nil panic 机制 | **⚠️ 部分冲突** |
| borrow escape 表示风险 | Go 只有值传递/指针传递 | **✅ 冲突** |
| memory leak 可能发生 | GC 回收不可达对象 | **✅ 冲突** |
| double free 可能发生 | 无 manual free | **✅ 冲突** |

#### 逐条验证表

| # | Issue ID | 类型 | Confidence | Go 语义分析 | 判定 | 理由 |
|---|---------|------|------------|------------|------|------|
| 1 | OMI-001 | null_dereference | medium | `runtime.alloc` 返回的指针由 GC 管理 | **FP ❌** | 调查报告确认: "Go GC 管理内存" |
| 2 | (PtrOwner) | use-after-free | — | GC 保证对象在使用期间存活 | **FP ❌** | 调查报告: "runtime.alloc UAF → FP" |

## 八、Known Limitations

1. **TP 率偏低 (~3-8%)**: 558 个 issue 中仅 ~19-46 个是真实 bug。主要原因是测试 corpus 包含大量成熟的开源库 (SQLite, curl, libuv, abseil)，这些库的基础Memory Safety bug 早已被Fix。
2. **sqlite3 仍占主导**: 240/558 = 43%。一个项目的 issue 数量仍占近半。
3. **Go 语言不支持**: gnark_test (Go/Tinygo) 的 6 个 issue 几乎全部是 FP。OmniScope 的分析模型基于 C/Rust 手动内存管理，不适用于 GC 语言。
4. **Compiler builtin 误报**: `__strcpy_chk`, `__snprintf_chk`, `__memcpy_chk` 等编译器 FORTIFY_SOURCE 内置函数被标记为 risky call，Actual是安全的。
5. **POSIX API 误报**: pthread_*, setsockopt, inet_pton, getaddrinfo 等标准系统调用在成熟的系统库中被大量使用，不是 bug。
6. **测试集偏斜**: ZKP 加密项目 (Rust/Zig) 占 50%，C 项目仅 3 个大型成熟库。缺少真实的 buggy C 项目来衡量 TP 检出能力。
7. **blst 的 1 个 issue 无法确定**: 需要 .ll IR 文件才能判断是 transmute 相关的真问题还是残留 FP。
