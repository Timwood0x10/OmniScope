## 二、真实情况

### 2.1 代码质量

| 问题 | 严重程度 |
|------|----------|
| 未初始化指针直接用 | 真的会崩 |
| 变量名拼错 | 编译都不一定能过 |
| page_allocator 到处撒 | 内存泄漏 |
| 悬空指针返回 | 用着用着就崩 |
| 错误全部 catch return 吞掉 | 鬼知道出了什么问题 |

**评价**: 典型的 "先把功能跑起来再说" 的垃圾代码，做安全工具简直是对安全的侮辱。

### 2.2 内存管理

满大街的 `std.heap.page_allocator`，这是给测试用的，不是给生产用的。

```zig
// 谁写的？page_allocator 能释放吗？
.map = std.AutoHashMap.init(std.heap.page_allocator),
```

**后果**: 程序跑久了内存一直涨，最后 OOM。测试环境跑个几分钟没问题，放服务器跑几天就升天。

### 2.3 错误处理

```zig
// 看看这写的什么鬼
var buf = std.ArrayList(u8).initCapacity(alloc, 256) catch return;
```

内存分配失败你就直接 return？调用方知道发生了什么吗？日志都不打一个？

还有满屏的 `unreachable`，你知道这玩意儿在 release mode 会直接 abort 吗？插件传个错数据进来，整个程序就炸了。

### 2.4 悬空指针

```zig
// 直接返回 LLVM 内部的字符串指针
return std.mem.span(c.LLVMGetValueName(func));
```

这种代码能跑是因为运气好，LLVM 没回收这块内存。等哪天换个 LLVM 版本，或者上下文变了，指针就飞了。

### 2.5 污点传播

```zig
// 看看这个逻辑
if (visited.contains(edge.callee)) continue;
visited.put(edge.callee, {}) catch continue;
```

刚遍历到一个节点就标记 visited，同一个污点源通过不同路径传播就直接跳过了。**这意味着有些漏洞根本检测不出来**。

这可是核心功能啊大哥！
